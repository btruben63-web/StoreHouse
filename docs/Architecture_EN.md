# Architecture

This document is based exclusively on the current code. For installation and operations, see [Runbook_EN.md](Runbook_EN.md); for history, see [CHANGELOG_EN.md](CHANGELOG_EN.md).

## 1. Overview

StoreHouse is a .NET 10 (C# 14) solution with two independent HTTP services and one PostgreSQL database per service:

- **App.IdentityServer** authenticates users and issues JWT tokens.
- **Product.Api** exposes product and stock management (9 endpoints under `/api/products`) and validates the tokens issued by the IdentityServer.

The functional description of the endpoints and the demo users are in the [README](../README_EN.md).

## 2. Components

| Component | Responsibility |
|---|---|
| `App.IdentityServer` | Duende IdentityServer + ASP.NET Identity (users, roles, lockout). Exposes `POST /api/auth/login` and the OIDC endpoints (`/connect/token`, `/.well-known/openid-configuration`). |
| `Product.Api` | Presentation layer: controllers, JWT Bearer authentication, role-based authorization, Swagger, global error handling (`ProblemDetails`). |
| `Product.Application` | Use cases (CQRS with MediatR), validation (FluentValidation), DTOs, mapping (Mapster), `Result` pattern, persistence contracts. Depends on neither HTTP nor EF Core. |
| `Product.Domain` | Entities (anemic model), `StockMovementType` enum and validation constants (`ProductConstraints`). |
| `Product.Infrastructure` | EF Core + Npgsql: `ProductDbContext`, table configurations, migrations and seed, repository, read queries, `UnitOfWork`. |
| `Product.Api.UnitTest` | Unit tests (xUnit v3 + Moq) covering `Product.Api` and `Product.Application`. |

## 4. Project dependencies

```
Product.Api ──► Product.Application ──► Product.Domain
     │                                       ▲
     └────────► Product.Infrastructure ──────┘
                (also references Product.Application)

App.IdentityServer          (no references to the Product.* projects)
Product.Api.UnitTest ──► Product.Api, Product.Application
```

`Product.Api` registers the `Product.Infrastructure` implementations through `AddInfrastructure`, and `Product.Application` defines the interfaces (`IProductRepository`, `IProductQueries`, `IUnitOfWork`).

## 5. General flow

1. The client calls `POST /api/auth/login` on the IdentityServer. `AuthController` sends a *password grant* request to `IdentityServer:TokenEndpoint` and returns `accessToken`, `tokenType` and `expiresIn`. Invalid credentials return `401`; any other token endpoint error throws an exception (`500`).
2. The client sends `Authorization: Bearer <token>` to `Product.Api`. JwtBearer validates the issuer, audience (`product.api`) and lifetime, and reads the role from the `role` claim.
3. The controller sends a command/query through `ISender`. The MediatR pipeline runs, in order: `LoggingBehavior` → `ValidationBehavior` → handler.
4. The handler returns a `Result`/`Result<T>`. Commands use `IProductRepository` + `IUnitOfWork`; queries use `IProductQueries`.
5. `ResultExtensions` converts errors into `ProblemDetails` (`application/problem+json`) with `code` and `traceId`:

| `ErrorType` | HTTP |
|---|---|
| `Validation` | 400 |
| `NotFound` | 404 |
| `Conflict` | 409 |
| `BusinessRule` | 422 |
| Others | 500 |

Unhandled exceptions go through `GlobalExceptionHandler` (`500`; the exception detail is only included in `Development`). `401`, `403` and route `404` responses also use `ProblemDetails` (`UseStatusCodePages`).

## 6. Data model (`StoreHouse` database)

| Table | Notes |
|---|---|
| `Product` | `Id` generated by the `ProductIdSequence` sequence (100000–999999, no cycle, starting at 100011); price > 0 (`CHECK`); soft delete (`IsDeleted`, `DeletedAt`, `DeletedBy`); `Version` mapped as a *row version* (`xmin`). |
| `Stock` | 1:1 with `Product` (PK = `ProductId`); `CHECK (Quantity >= 0)`; index on `Quantity`. |
| `StockMovement` | Movement history (`Initial`, `Increase`, `Decrease`) with `QuantityAfter` and `CreatedBy`. |

All three types have a global filter that hides deleted products. The initial migration inserts 10 seed products (IDs 100001–100010). The IdentityServer database (`StoreHouseIdentity`) uses the ASP.NET Identity schema, seeded with 2 users (`Admin`, `Manager`), 2 roles and the corresponding role claims.

## 7. Authorization in Product.Api

| Endpoint | Rule |
|---|---|
| `GET` (list, by id, `search`, `stock-level`) | Anonymous |
| `POST /api/products`, `DELETE /api/products/{id}` | `Admin` role |
| `PUT /api/products/{id}`, `add-to-stock`, `decrement-stock` | Any authenticated user (the API does not explicitly check the `Manager` role) |

## 9. Identifiable architectural decisions

| Decision | Implementation |
|---|---|
| CQRS | Commands use the repository with *tracking*; queries (`ProductQueries`) use `AsNoTracking` and `ProjectToType<ProductDTO>`. |
| Expected errors via `Result` | Handlers return an `Error` instead of throwing; the Application layer knows nothing about HTTP. |
| 6-digit IDs | PostgreSQL sequence as the default value of the `Id` column. |
| Concurrent stock | Conditional `ExecuteUpdate` (`Quantity >= @q` / upper limit) inside a transaction with an *execution strategy* (`EnableRetryOnFailure(3)`), together with the `StockMovement` record. |
| Concurrent `PUT`/`DELETE` | Optimistic concurrency; `DbUpdateConcurrencyException` → `ConcurrencyConflictException` → `409`. |
| Soft delete | Global EF Core filter; stock history is preserved. |
| Pagination | *Keyset* on `Id` (`lastItemId`, `pageSize` 1–50, default 5); response `items`/`nextCursor`/`hasMore`. |
| Name search | `ILIKE` with escaping of `%`, `_` and `\` (`LikePatternEscaper`) and a GIN trigram index. |
| `DbContext` pooling | `Product.Infrastructure` uses `AddDbContextPool<ProductDbContext>`, which reuses context instances across requests. The context holds no state of its own and `UnitOfWork` calls `ChangeTracker.Clear()` at the start of each transaction. The IdentityServer uses `AddDbContext` (no pooling). |
| *Connection pooling* | Handled by Npgsql and configured in the connection string: `Pooling=true` and `Maximum Pool Size=50` (plus `Minimum Pool Size=0` in `Product.Api`) in `docker-compose.yml` and in the README examples. Not set in `appsettings.json`. |
| Migrations on startup | Both services call `MigrateAsync()` on startup. |
| In-memory clients and scopes | Defined in `IdentityServerConfig` from `IdentityServerSettings`; users live in the database. |
| OAuth flow | *Resource owner password* with a single client (`storehouse.swagger`, default value in `appsettings.json`), no refresh token. |
| Claims | `DistinctClaimsProfileService` removes duplicate claims from the token. |
| Time | `TimeProvider` injected into the handlers. |

## 10. Validation, security and concurrency

**Validation (MediatR + FluentValidation)**
- Each command/query has an `AbstractValidator`, with shared rules in `ProductRules` and limits in `ProductConstraints`.
- `ValidationBehavior` runs all validators before the handler, groups messages by property and returns `Error.Validation` (`400`). If validation fails, the handler is not executed.
- *Model binding* errors follow the same format (`InvalidModelStateResponseFactory`).
- The database repeats part of the rules as a second line of defense (`CHECK` constraints on price, stock and movements, and maximum column lengths).

**Security**

| Risk | Measure in the code |
|---|---|
| SQL injection | There is no hand-written SQL (`FromSql`/`ExecuteSql` are not used): EF Core LINQ and `ExecuteUpdate` generate parameterized queries. In `ILIKE`, the pattern is passed as a parameter and the input's `%`, `_` and `\` are escaped. |
| Invalid input | Validation of IDs, lengths, prices, quantities and pagination (see above). |
| Unauthorized access | JWT validated (issuer, audience, lifetime, 30 s clock skew); `Admin` required for `POST`/`DELETE`; login lockout after 5 failures / 5 min; seed passwords stored only as hashes. |
| Information leakage | Exception details only appear in `Development`; secrets come from configuration (User Secrets / `.env`), not from the code. |
| Transport and containers | `UseHttpsRedirection` and `UseHsts` (outside `Development`); images run with `USER $APP_UID` (non-root). |

**Concurrency (*race conditions*)**

| Scenario | Technique |
|---|---|
| Two requests generate the same ID | PostgreSQL sequence (atomic across instances). |
| Two requests change stock at the same time | A single conditional `UPDATE`, with no read-then-write in the application: `Quantity >= @q` when decreasing and an upper limit when increasing. If it affects 0 rows, the handler tells "does not exist" apart from "insufficient stock/limit exceeded". |
| Inconsistent stock and history | Update and `StockMovement` in the same transaction (rolled back if the `Result` fails). |
| Negative stock | `CHECK (Quantity >= 0)` as the last line of defense. |
| `PUT`/`DELETE` on stale data | Optimistic concurrency with `xmin` → `409`. |

Known limitation of the automatic retry of stock operations: see [Runbook_EN.md](Runbook_EN.md#6-known-issues).

## 11. Not present in the code

Health checks, rate limiting, API versioning, a CI pipeline, integration tests and a configured log sink (only the default ASP.NET Core logging). The unit tests do not cover the repository, SQL queries, `UnitOfWork`, migrations or `App.IdentityServer`.
